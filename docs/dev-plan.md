Think Twice — תכנית פיתוח: פרוטוטייפ  
מבוסס על "המסמך המציג — הכלי הטיפולי במלואו" (גרסה 4\)

תאריך: 11.6.2026 | גרסה: v1  
מקדם: Phase 2 (אפיון) \+ Phase 3 (פיתוח) בתכנית הפעולה, בהיקף פרוטוטייפ

\========================================  
1\. מטרה ו-End Game  
\========================================

המטרה: פרוטוטייפ עובד של Think Twice שמממש את המסמך המציג במלואו — ראיון חצי-מובנה בשבעה שלבים, בהובלת דמות המראיין, עד הכרעה חדה.

הגדרת "מוכן" (End Game):  
נטלי, בחשבון Claude שלה, ללא שום מעורבות של רן מעבר להתקנה ראשונית, יכולה:  
1\. לפתוח את הכלי ולהריץ ראיון מלא על מקרה (אמיתי או מדומה) — מחוזה הפתיחה ועד סיכום המסע.  
2\. לצפות ב"מצב מדריך" — ה-Scorecard החי, החלטות הניתוב והמדדים — תוך כדי הראיון.  
3\. לייצא תמליל \+ State לקובץ ולשתף לתיקיית ה-Drive.  
4\. לחזור על התהליך כמה שתרצה, על חשבון המנוי שלה, בלי תלות טכנית ברן.

מחוץ לתכולה (Out of Scope לפרוטוטייפ): הרשמה/סיסמאות, חיוב, ממשק web עצמאי, ריבוי משתמשים, שמירת היסטוריה בענן. (ראו פרק 7 — גשר לעתיד.)

\========================================  
2\. עקרונות מנחים להנדסה (נגזרות מהמסמך המציג)  
\========================================

1\. המודל מציע — הקוד מכריע. ה-LLM לעולם אינו מחליט על מעבר שלב. הוא מדווח ציוני Slots, דגלי התנגדות וסתירות; ה-Router הדטרמיניסטי מכריע לפי כללי הפרוטוקול (סף רך, מיצוי, מגן עומס, re-open). זה המימוש ההנדסי של "שיחה חופשית מקדימה, גיליון נסתר מאחור".  
2\. עיקרון 0 בקוד: ה-Router לעולם לא מאציל ניווט למשתמש. נקודות ההחלטה היחידות ב-UI: אישור סיכום (כפתורי "מדויק / לתקן") וההכרעה בשלב 7\.  
3\. פרומפטים הם תוכן, לא קוד. כל פרומפט (דמות, 7 סוכנים, מעריך) — מודול נתונים נפרד עם מספור גרסה. נטלי מתקנת ניסוח ← מתעדכן קובץ תוכן, לא קוד.  
4\. ליבה ניידת. שכבת ה-Orchestration היא לוגיקה טהורה ללא תלות ב-UI או בפלטפורמה — אותה ליבה תרוץ מחר בשרת ה-web. רק שכבת המודל (Adapter) מוחלפת.  
5\. עברית-RTL כאזרח ראשון. כל ה-UI והפרומפטים בעברית; בדיקות RTL בכל שלב.  
6\. פרטיות: אפס שרת. הכל רץ בחשבון של נטלי; תמלילים נשמרים רק היכן שהיא בוחרת לייצא.

\========================================  
3\. ארכיטקטורה מפורטת  
\========================================

3.1 חמש שכבות

שכבה 1 — UI (React, RTL):  
\- מסך צ'אט מינימלי: בועות שיחה, שדה קלט, חיווי "המראיין כותב".  
\- חוזה פתיחה כהודעה ראשונה קבועה.  
\- Signposting עדין: שורת מיקום ("מסדרים את הסיפור" / "איך הבנת את זה" / ...).  
\- כפתורי אישור סיכום ("מדויק" / "רוצה לתקן") — מופיעים רק בנקודות ולידציה.  
\- שלב 7: רינדור לוח ההכרעה כטבלה (אפשרות | יתרון | חיסרון) מתוך ה-State — הקוד בונה את הלוח, לא המודל.  
\- פעולות סשן: אירוע חדש, ייצוא תמליל+State (קובץ JSON/טקסט), ייבוא State (Re-entry).  
\- "מצב מדריך" (Clinician Debug Panel): מתג שפותח חלונית צד — State Document חי, Scorecard לכל שלב, החלטות Router אחרונות, מדדי KPI, דגלי התנגדות. כלי הולידציה של נטלי.

שכבה 2 — Orchestration (לוגיקה טהורה, ללא UI):  
\- Router: מכונת מצבים על 7 הנושאים. קלט: ציוני Slots ודגלים מהמעריך \+ מוני שאלות/מיצוי. פלט: הישאר / עבור לנושא N / re-open נושא K / הצג סיכום לאישור / הצג לוח הכרעה / עצירת בטיחות. אוכף: תלויות (5 דורש 2; 7 דורש 6), חד-כיווניות 6→7, אישור-משתמש כתנאי מעבר, מגן עומס (5–7 שאלות, 4–5 בשלב 5), saturation (2 תורות בלי חדש), סף רך (\~80%).  
\- StateDocument: אובייקט JSON יחיד — facts, thoughts (כולל מוגלה ותיוג ADHD), feelings (רגש+עוצמה+הד עבר), reactions (אוטומטית/מתוכננת), basket (חלופות), board (לוח ההכרעה), decision (סוג, נימוק, חבילה), coverage (ציוני Slots לכל נושא: 0/1/2/U), meta (פתח שאלה, דגלי התנגדות, מונים, KPI, חוטים שמורים).  
\- PromptBuilder: מרכיב לכל תור: פרומפט דמות גלובלי \+ רשימת "אסור" \+ פרומפט הסוכן הנוכחי \+ תמצית State (לא כל ההיסטוריה — חיסכון טוקנים ויציבות) \+ K התורות האחרונות \+ הוראת פלט מובנה.  
\- ResponseParser: מאמת את ה-JSON שחוזר; תיקון/קריאה חוזרת במקרה פלט שבור; הפרדה בין message (מוצג) ל-evaluation (נסתר).

שכבה 3 — תוכן (פרומפטים):  
\- פרומפט דמות גלובלי: תכונות המראיין, הקול, עקרונות-העל, רשימת ה"אסור" (כולל: לא לסיים תור בלי שאלה אחת בדיוק; לא תפריטים; לא המלצות; לא השתלת פרשנות).  
\- 7 פרומפטי סוכנים: מטרה, Slots, שאלות מנחות, מבחני איכות (מצלמה/ציטוט/גרנולריות/התנהגותי/גוף-שלישי/חדות/חבילה), תנאי דיווח.  
\- פרומפט מעריך (משולב בכל קריאה): עדכן Slots, זהה התנגדות (הימנעות/בריחה/הצפה/ציניות), זהה סתירה עובדתית, סווג חדות תשובה (בשלב 7), המלץ פתח שאלה.  
\- פורמט פלט אחיד: JSON עם message \+ evaluation. קריאת מודל אחת לתור.

שכבה 4 — Model Adapter:  
\- ממשק complete(prompt) יחיד. בפרוטוטייפ: יכולת ה-AI של Artifacts (על חשבון המשתמש הצופה). בעתיד: קריאת API מאחורי שרת. נקודת ההחלפה היחידה.

שכבה 5 — בטיחות:  
\- בדיקת קדם לכל הודעת משתמש (מילות מפתח \+ שיקול המודל): אזכורי פגיעה עצמית/מצוקה חריפה ← עצירה בטוחה: הודעה אמפתית קבועה, הצעת פנייה לגורם מקצועי/קו סיוע, השהיית הראיון. בלי אבחון, בלי טיפול. (מממש את "גבולות הכלי", חלק ח במסמך.)

3.2 זרימת תור בודד  
הודעת משתמש ← בדיקת בטיחות ← PromptBuilder ← קריאת מודל ← ResponseParser ← עדכון StateDocument ← Router מכריע ← (אם מעבר/סיכום: תוספת מתאימה להודעה) ← הצגת שאלת המראיין \+ עדכון מצב מדריך.

3.3 מיפוי רכיב ← מסמך נטלי (בדיקת כיסוי)  
\- שתי היכולות (חלק א): שכבה 3 \= המודל המקצועי; שכבות 1–2 \= ניהול השיח.  
\- הסיטואציה (חלק ב): שלושת תרחישי הכניסה נתמכים בפרומפט Intake; חוזה פתיחה בכניסה.  
\- עיקרון 0 (חלק ג): Router בלעדי על ניווט; משולש האחריות בחוזה הפתיחה; ההכרעה רק של המשתמש.  
\- דמות המראיין (חלק ד): פרומפט גלובלי \+ lint אוטומטי (שאלה אחת, בלי תפריטים, משפטים קצרים).  
\- התנגדויות (ד.3): דגלי מעריך \+ משתנה פתח-שאלה ב-meta \+ כללי Router.  
\- מאחורי הקלעים (ד.4): coverage, saturation, load guard, re-open — קוד.  
\- שבעת השלבים (חלק ה): מכונת המצבים \+ 7 פרומפטים.  
\- מקרה הבשר (חלק ו): תסריט הזהב המרכזי בבדיקות.  
\- מדדים (חלק ט): מודול KPI — דלתא רגש, יחס אני/הוא, מדד שינוי, סוג הכרעה.  
\- גבולות (חלק ח): שכבת בטיחות \+ lint "אסור להמליץ".  
\- שאלות המשוב (חלק י): פרוטוקול המשוב בשלב 7 של התכנית.

\========================================  
4\. תכנית הפיתוח בשלבים  
\========================================

עיקרון השלביות: כל שלב מסתיים בתוצר שנבדק בנפרד, בתנאי יציאה מוגדרים, וניתן לעצירה/המשך נקי. מסלול כפול: שלב 1 מספק לנטלי כלי התנסות מיידי בזמן שהאפליקציה נבנית.

שלב 0 — Spike פלטפורמה (יום עבודה)  
מטרה: אימות יכולות ה-Artifacts בחשבון Claude עדכני.  
תכולה: ארטיפקט בדיקה זעיר — קריאת מודל מתוך Artifact, פלט JSON מובנה, עברית RTL, שיתוף בקישור לחשבון אחר (בדיקה מול חשבון של נטלי או חשבון שני שלך), מדידת השהיה.  
בדיקות ותנאי יציאה: כל היכולות אומתו ← Go למסלול Artifact. אם שיתוף/קריאות מודל לא זמינים ← תכנית חלופית מוכרזת: המסירה לנטלי תתבסס על מסלול הפרומפט (שלב 1\) \+ הרצת ה-Artifact מחשבונך בפגישות משותפות, עד פתרון.

שלב 1 — אב-טיפוס פרומפט: "מסלול הזהב" (2–4 ימים)  
מטרה: ולידציה קלינית מוקדמת של התוכן — לפני ובמקביל לקוד.  
תכולה: פרומפט-על אחד (Claude Project Instructions) שמממש: דמות, חוזה פתיחה, 7 שלבים, שאלה-אחת, אישורי סיכום, לוח הכרעה, מבחן חבילה, רשימת "אסור". בלי state חיצוני — המודל מנהל הכל בהקשר השיחה.  
בדיקות: הרצת 4 מקרי הדוגמה (בשר, חבר מתייעץ, מורה, חברה עסוקה) כתסריטי זהב; צ'ק-ליסט עקרונות על כל תמליל (ראו 5.2); תיקוני ניסוח.  
תנאי יציאה: 4/4 תסריטים מגיעים להכרעה חדה תוך עמידה בצ'ק-ליסט.  
תוצר לנטלי: קובץ Instructions \+ דף הדבקה-לפרויקט של עמוד אחד. נטלי מתחילה להתנסות ולהזין משוב כבר עכשיו (על חשבונה, בפרויקט שלה).

שלב 2 — שלד האפליקציה: State \+ Router (שבוע)  
מטרה: ההיגיון הדטרמיניסטי עובד — בלי LLM.  
תכולה: שכבות 1–2 עם Model Adapter מדומה (Mock שמחזיר תשובות תסריטאיות): UI צ'אט RTL, StateDocument מלא, Router על כל כללי המעבר, כפתורי אישור, ייצוא/ייבוא.  
בדיקות (פונקציונליות, אוטומטיות על fixtures): מטריצת מעברים — לכל נושא: כניסה, מיצוי, סף רך, מגן עומס, re-open, תלות 5←2, חד-כיווניות 6→7; שלמות state (אף עובדה לא נמחקת; re-open מוריד ציון Slot); ייבוא state משחזר סשן זהה; אישור משתמש חוסם/משחרר מעבר.  
תנאי יציאה: כל בדיקות המטריצה עוברות; הדגמת זרימה מלאה עם Mock.

שלב 3 — סוכני הליבה 1–4 (שבוע–שבועיים)  
מטרה: ראיון אפר"ת אמיתי (עובדות←פרשנות←רגש←תגובה) עם מודל חי.  
תכולה: פירוק פרומפט-העל משלב 1 ל-4 פרומפטי סוכנים \+ פרומפט מעריך \+ פורמט JSON; חיבור ל-Adapter אמיתי; מצב מדריך בסיסי.  
בדיקות: לכל סוכן בנפרד — שיחות fixture (קלט נתון ← ציוני Slots צפויים בטולרנס מוגדר); מבחני איכות בשופט-LLM: מצלמה (Intake לא מקבל פרשנות כעובדה), ציטוט, גרנולריות, התנהגותי; lint אוטומטי: שאלה אחת בדיוק בכל תור, אפס ביטויים אסורים; בדיקת הפרדה (רגש שעולה בשלב 2 נרשם ולא נחקר).  
תנאי יציאה: 4 הסוכנים עומדים ביעדי הבדיקות על מקרה הבשר \+ מקרה נוסף.

שלב 4 — סוכנים 5–7: Transform והכרעה (שבוע)  
מטרה: החצי השני של המסע — עד הכרעה חדה.  
תכולה: פרומפטי Transform / יצירת חלופות / הכרעה; בניית לוח ההכרעה בקוד מתוך ה-basket; מסווג חדות (חדה/דחייה-מובנית/עמומה); מבחן חבילה; מבחן "או-או" (מיזוג ← חזרה לשלב 6).  
בדיקות: מבחן בעלות (הסוכן לא משתיל פרשנות — שופט-LLM); מבחן עיגון (חלופית לא סותרת עובדות); דלתא רגש נמדדת; תרגילי עמימות: "אולי", "גם וגם", "נראה" ← המערכת מחדדת ולא סוגרת; דחייה מובנית ← נקודת חזרה נרשמת; הכרעה באוטומט המקורי מתקבלת בלי שיפוט.  
תנאי יציאה: מקרה הבשר רץ מקצה לקצה באפליקציה ומסתיים בהכרעה חדה \+ מבחן חבילה.

שלב 5 — מנגנונים רוחביים ובטיחות (שבוע)  
מטרה: עמידות בשיחה אמיתית, לא רק במסלול הזהב.  
תכולה: פרוטוקול התנגדויות מלא (זיהוי הימנעות/בריחה \+ החלפת פתח שאלה \+ שמירת חוטים); הצפה רגשית (השהיה וויסות); ציניות; שכבת הבטיחות; signposting; חוזה פתיחה; Re-entry מלא.  
בדיקות (תסריטי פרסונה כתובים מראש): "הנמנע" (תשובות של מילה) ← נשאר בפתוח, מקטין, U אחרי שניים; "הבורח" (אסוציאציות) ← עובר לסגור, חוטים נשמרים, חוזר לפתוח; "המוצף" ← השהיית אג'נדה; "הציני" ← אי-מגננה; "מחפש העצה" ("מה אתה היית עושה?") ← החזרה לתהליך בלי המלצה; אדום-בטיחות: אזכור פגיעה עצמית ← עצירה בטוחה מיידית; נטישה באמצע ← ייבוא state ← המשך מאותה נקודה.  
תנאי יציאה: כל תסריטי הפרסונה עוברים; אדום-בטיחות עובר ב-100%.

שלב 6 — אינטגרציה, מדדים והקשחה (שבוע)  
מטרה: הפרוטוטייפ כולו, ברף איכות מוצהר.  
תכולה: ליטוש UI ועברית; מצב מדריך מלא; איסוף KPI מאומת; אופטימיזציית טוקנים (תמצות state); יציבות JSON.  
בדיקות E2E: 4 תסריטי הזהב \+ 2 מקרים חדשים שנטלי תנסח \+ תסריטי הקושי משלב 5 — הכל מקצה לקצה.  
רף קבלה כמותי (על מדגם התמלילים): 100% מהתורות עם שאלה מכוונת אחת בדיוק; 0 תפריטים/בקשות רשות; 0 המלצות; 4/4 תסריטי זהב מגיעים לסגירה חדה; ציוני שופט-LLM ≥ 4/5 באמפתיה, אי-שיפוטיות, בעלות; דלתא רגש נרשמת בכל ראיון מלא; re-entry משחזר נאמנה.  
תנאי יציאה: עמידה ברף \+ אישור שלך על חוויית השימוש.

שלב 7 — מסירה לנטלי ופרוטוקול משוב (יומיים)  
מטרה: ה-End Game עצמו.  
תכולה: שיתוף הקישור; "דף התקנה" של עמוד אחד בעברית (פתיחת הקישור, התחברות לחשבון שלה, הרצת מקרה, מצב מדריך, ייצוא תמליל לתיקיית Drive); תבנית משוב מובנית — דירוג 1–5 לכל שלב (אמפתיה/דיוק/קצב) \+ 15 שאלות המשוב מהמסמך המציג כרובריקה \+ שדה חופשי; גיליון תקלות בתיקייה.  
בדיקת קבלה (User Acceptance): נטלי מריצה לבד, מהקישור, ראיון מלא ראשון — בלי שום עזרה ממך — ומגישה משוב דרך התבנית. אם נדרשה התערבות שלך מעבר להתקנה ← חוזרים לתקן.  
תנאי יציאה: שני ראיונות מלאים עצמאיים של נטלי \+ טופס משוב ראשון התקבל.

\========================================  
5\. תכנית הבדיקות הרוחבית  
\========================================

5.1 בדיקות פונקציונליות (אוטומטיות היכן שניתן)  
\- מטריצת המעברים המלאה (שלב 2\) — מורצת מחדש בכל שינוי Router.  
\- שלמות State: אין אובדן עובדות; coverage עקבי; חוטים שמורים נשלפים.  
\- חוסן פלט מודל: JSON שבור ← retry ותיקון בלי קריסה.  
\- ייצוא/ייבוא: שוויון state מלא אחרי מחזור.  
\- UI: RTL בכל רכיב; כפתורי אישור רק בנקודות ולידציה; לוח הכרעה נבנה מה-state בלבד.

5.2 בדיקות איכות שיחתית (Lint אוטומטי \+ שופט-LLM)  
Lint לכל תור: בדיוק שאלה מכוונת אחת; אורך תור עד \~3 משפטים \+ שאלה; אפס מונחים קליניים כלפי המשתמש; אפס ביטויי תפריט/רשות/המלצה (רשימה שחורה: "תרצה ש...", "אפשרות א או ב", "כדאי לך", "אני ממליץ"...).  
שופט-LLM לכל תמליל (רובריקה 1–5): אמפתיה מדויקת; אי-שיפוטיות; הקשבה אקטיבית (השאלה נגזרת מהתשובה האחרונה); בעלות (אפס השתלות); עברית טבעית. סף: ≥4.  
KPI: נאספים ומוצגים — דלתא רגש, יחס אני/הוא, מדד שינוי, סוג הכרעה, שאלות-לשלב.

5.3 בדיקות קליניות (נטלי)  
\- סימולציות פרסונה לפי תרחישי הכניסה (סוער / אחרי-הפעולה / לקראת-אירוע).  
\- רובריקת 15 השאלות מהמסמך המציג — כל שאלה נבדקת מול חוויית שימוש אמיתית.  
\- ולידציה של מבחני האיכות (מצלמה/ציטוט/גרנולריות/התנהגותי) על תמלילים אמיתיים.  
\- ולידציה של ספי מנות-השאלות והמתח הבריא.

5.4 בדיקות עמידות וקצה  
פרסונות ההתנגדות (5 התסריטים משלב 5); סיפור ארוך ומפותל (ניהול הקשר); סתירה עובדתית באמצע (Dynamic Interruption — עצירה, שיקוף, תיקון); ניסיונות חוזרים לחלץ המלצה; נטישה וחזרה; שפה קשה כלפי דמויות בסיפור (נרשם בלי שיפוט).

5.5 בדיקות בטיחות (חובה, 100%)  
תסריטי מצוקה חריפה ← עצירה בטוחה עקבית; ניסוח ההפניה — באישור נטלי; תיעוד הגבול בדף ההתקנה.

\========================================  
6\. גשר לעתיד (לא בתכולה — מכוון בחירות היום)  
\========================================

היעד העתידי: שירות web ייעודי, רב-לקוחות, שם+סיסמה, חיוב לפי שימוש.  
מה בארכיטקטורה כבר מוכן: ליבת Orchestration ניידת (תרוץ בשרת Node כמו-שהיא); State schema יציב (יהפוך לרשומת DB); פרומפטים כתוכן מנוהל-גרסה; Model Adapter (יוחלף ב-API צד-שרת); ה-UI (React) יהגר כמעט במלואו.  
מה יתווסף אז בלבד: שרת דק (אימות, מפתח API מאוחסן צד-שרת, מדידת שימוש לחיוב, אחסון סשנים מוצפן), ניהול משתמשים, תשלומים, אבטחת מידע רגולטורית (פרטיות בריאות), והפעלת הדיסקליימר המשפטי (השאלה הפתוחה הקיימת).  
כלל: שום החלטה בפרוטוטייפ לא נועלת את המסלול הזה; כל קיצור דרך מתועד כ"חוב מוצהר".

\========================================  
7\. סיכונים ומיתונים  
\========================================

1\. יכולות פלטפורמה (קריאות מודל מתוך Artifact / שיתוף) השתנו ← שלב 0 מוקדש לכך; חלופה מוכרזת: מסלול הפרומפט כמסירה ראשונה.  
2\. סחף מודל (תשובות ארוכות, תפריטים, המלצות) ← רשימת "אסור" בפרומפט \+ Lint חוסם \+ retry אוטומטי עם הערת תיקון.  
3\. הקשר מתארך/יקר ← PromptBuilder שולח תמצית state \+ K תורות אחרונים בלבד; מדידת עלות-לראיון בשלב 6\.  
4\. אובדן סשן (אין אחסון מתמשך ב-Artifacts) ← ייצוא/ייבוא state; הנחיה לנטלי לייצא בסוף כל הרצה.  
5\. RTL/עברית ברכיבי UI ← בדיקת RTL בכל שלב, החל מה-Spike.  
6\. פרטיות תכנים אישיים בסימולציות ← אפס שרת; התמלילים אצל נטלי בלבד; הנחיה לא להזין פרטים מזהים של אחרים.  
7\. עומס על נטלי ← מסלול כפול: היא מתחילה בשלב 1 הקל; האפליקציה מגיעה אליה רק אחרי רף שלב 6\.
